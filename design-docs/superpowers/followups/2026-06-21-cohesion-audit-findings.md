## Per-subsystem architecture notes

### py:chart-core
_Role:_ The fluent, immutable declaration-API spine: assembles marks/encodings/transforms/config/overrides/interactivity into a Rust ChartSpec.
_Note:_ chart.py is a genuine god module (3953 lines) that fuses at least five responsibilities into the Chart class plus a layer of free functions: (1) the fluent builder surface (mark_*, encode, properties, axis, coord, facet), (2) composite-mark desugar orchestration (_resolve_pending and ~9 module-level desugar helpers), (3) layered-transform routing (_resolve_layer_aggregates/_resolve_layer_bins/_NamedTransform/_transforms_to_json_list_named), (4) spec assembly (to_spec/_build_encoding_specs), and (5) interactivity/param plumbing (_collect_params, selections, conditionals). The ConfigureMixin/configure.py/_override_apply.py split is actually the cleanest part of the subsystem — config logic does NOT leak across the three; each has one clear job. The real cohesion damage is concentrated in chart.py itself: a 265-line god-method, a hand-rolled value-class idiom in position.py that drifted from the dataclass idiom used everywhere else, and several copy-pasted invariant checks (reactive-param collision, name-dedup) that should be single helpers.
_Themes:_ god-module / responsibility fusion in chart.py, sibling-drift in value-class construction idioms (position vs selection/configure), duplicated invariant checks (param-collision, name-dedup) that want one helper, mixed-abstraction desugar orchestration with per-mark special-casing

### py:composition
_Role:_ Multi-chart composition wrappers (Concat/Joint/Repeat/ClusterMap/Layer) plus the scene/packed-byte merge machinery and the annotation primitive system that decorate composed figures.
_Note:_ composition.py is a well-factored class family: _ChartLike centralizes save/show/export plumbing, _CompositeBase owns figure chrome and a parameterized symmetric-concat strategy, and the interactive merge helpers funnel through a shared _PlacedChild + _assemble_placed_children seam. The recent figure-chrome consolidation (D10/#8) genuinely unified what used to be five drifting copies. The remaining cohesion problems are localized: validation logic that was extracted into helpers but not adopted by every sibling, a hand-typed empty-scene literal that drifts from its canonical constructor, and a per-child render loop copy-pasted across the four grid helpers. The sharpest boundary smell is outside composition.py proper: ferrum ships TWO parallel annotation vocabularies (annotations.py annotate_* returning Charts, and the annotation/ package returning dataclasses) that overlap conceptually but diverge in naming, return shape, and which renderer path they take.
_Themes:_ two-parallel-annotation-systems, extracted-helper-not-adopted-by-siblings, copy-paste in merge helpers, correctness-by-discipline in __copy__

### py:marks
_Role:_ Desugar the public composite/statistical/diagnostic mark methods (declared on two Chart mixins) into primitive multi-layer ChartSpecs plus Rust transforms, returning a uniform MarkDesugarResult that Chart._resolve_pending threads back into the chart.
_Note:_ The subsystem is two clean layers: thin mixin methods in the top-level `_marks_{statistical,diagnostic}.py` (the public `Chart.mark_*` surface, all delegating through one helper `_set_composite_mark`) and the `marks/` subpackage that holds the actual `desugar_*` expansion functions. That layering is intentional and sound — the `_marks_*.py` files are NOT scar tissue from a half-finished migration to `marks/`. The real drift is internal to the desugar family: the codebase migrated from a legacy "N-tuple" return protocol to a typed `MarkDesugarResult`, but only the implementations were updated — return annotations (three competing styles), every "Returns" docstring, and every doctest still describe the dead tuple protocol. Three near-identical structural conveniences (mixin/desugar naming collision, per-desugar `register_layer_names` duplication, a stale `warn_once` claim contradicting a `raise`) round out the picture.
_Themes:_ incomplete migration from tuple-protocol to MarkDesugarResult (annotation + docstring + doctest drift), sibling drift across the three desugar families (composite vs statistical vs diagnostic), correctness-by-discipline duplication (register_layer_names mirrors built layer names with no guard), stale/contradictory docstrings that survive only because doctests are not run

### py:encoding-scales
_Role:_ Declares the encoding-channel value objects (X/Y/Color/Size/...), their kwarg-honoring contract, the Python data-transform constructors, and programmatic palette access — the user-facing declaration surface that lowers to the Rust ChartSpec.
_Note:_ This is a sibling-family subsystem: ~35 channel classes that should be near-identical thin wrappers over ChannelBase, plus a parallel dict-returning transform-declaration surface (transforms.py) and a hand-mirrored palette table (color.py). The conceptual boundary is clean (Python declares, Rust computes), and ChannelBase does most of the real work well. What feels off is that the family's shared contracts are expressed three different ways depending on which file you land in: stack-offset validity is redefined in three modules, the "honored kwargs" set is named _RENDERED_HONORED in two files with two different memberships, format-type vocabulary is camelCase in text channels and snake_case in positional channels, and transforms.py declares the same conceptual things as the encoding channels but with none of the value-class discipline. Correctness currently rides on the warn-once guard and the serializer agreeing by hand-maintained coincidence rather than by a single source of truth.
_Themes:_ sibling drift across the channel family (names, vocab, validation), duplicated validation constants / source-of-truth fragmentation, correctness-by-discipline instead of by construction, paradigm split: value-class encodings vs dict-function transforms

### py:figure-functions (src/ferrum/plots/)
_Role:_ The user-facing figure-function layer: model-diagnostic charts (roc/residuals/shap/...) and seaborn-style declarative charts (displot/pairplot/...), each resolving an input into a source and delegating to a builder that returns a composed Chart.
_Note:_ Two distinct API families share one package: a "model-diagnostic" family (classification, regression, explanation, model_selection, clustering, ranking, decision_boundary) that flows public-wrapper -> _resolve_source -> _*_from_source builder, and a "seaborn declarative" family (distribution, matrix, lmplot/regplot) that takes data/x/y and builds inline with no builder split. _helpers.py is a genuine shared core for the first family (_resolve_source, _finalize_chart, metric injectors) but the families have drifted on the most prominent surfaces: the first-positional parameter name has four variants (model/source/data/X), the compare= keyword exists in only one of seven model-diagnostic modules, the same Cook's-threshold concept has two names, composite-returning functions disagree on their return annotation, and DataFrame coercion is reinvented three ways. None of this violates the hard constraints; it is cohesion drift in a fast-grown family.
_Themes:_ sibling-drift across the figure-function family (param naming, compare=, return shapes), incomplete unification / scar tissue (dead imports, deprecated shims, three coercion idioms), two-paradigm structure: builder-split diagnostic family vs monolithic seaborn family, leaky-internal / hidden cross-module coupling

### py:diagnostics-engine
_Role:_ Adapt fitted sklearn estimators (or raw prediction arrays) into long-form polars DataFrames of model-diagnostic derived data, and expose that data through two parallel surfaces: a ModelSource compute layer and a FerrumVisualizer render layer.
_Note:_ The sources/ (compute) vs visualizers/ (render) split is the right boundary and is mostly clean: visualizers own `_materialize` (headline metrics) + `_build_chart` (delegate to `_*_chart_from_source` builders), sources own derived-data DataFrames. The compute split into per-domain mixins + a shared `_curve_frames` kernel-assembly module is genuinely elegant. The cohesion damage is concentrated at two seams: (1) the `_PrecomputedSource` adapter duplicates several source methods by hand instead of sharing the same `_curve_frames` path the docstring promises is "exactly one implementation per concept", and (2) the FerrumVisualizer family has drifted in how it honors its own contracts (`has_score` flag, `_materialize`/`_build_chart` vs `fit` override, where compute happens).
_Themes:_ sibling-drift across the visualizer family, abstraction inversion: gain/lift bypass the shared curve-frame kernel, duplicated Arrow-coercion and CI/aggregation boilerplate, return-shape / contract drift (has_score, cluster dtype)

### py:render-interactive
_Role:_ Owns the Python-side dispatch from a declared Chart/composition into the Rust render engine and the assembly of every output artifact (SVG, PNG, PDF, interactive HTML, notebook display).
_Note:_ The subsystem has a clean conceptual spine: _render_inputs() assembles the (spec, data, viewport, theme, chart_config) tuple once, the static path feeds it to render_svg/render_interactive, and display.py owns format routing. The problem is the spine forks three ways and then the forks drift. _Themes:_ sibling-drift across the three save() dispatchers, incomplete unification (canonical title accessor bypassed by 2 of 3 callers), responsibility leakage in _render.py (render orchestration + annotation-coord math), leaky/dead internal API on the interactive surface

### py:themes
_Role:_ Defines the immutable Theme value class, the twelve built-in named themes, and the per-thread context-default theme controls, and serializes a theme to the flat key dict the Rust renderer consumes.
_Note:_ A small, mostly-clean value-object subsystem: Theme is a correctly immutable, hashable, equality-comparable wrapper over a sparse dict, and the render-time cascade (per-chart `chart._theme` > `get_default_theme()` context-default > Rust built-in defaults) is resolved in exactly one place (`_render.py:604-605`), which is the right design. The conceptual boundary that feels off is the theme-key *contract*: it is asserted twice — once as Python's `Theme._KNOWN_KEYS` frozenset and once as Rust's `ThemeOverridesSpec` (`deny_unknown_fields`) struct — and the two copies have already drifted (per-level grid keys), with a third hand-maintained color-key list (`_COLOR_KEYS`) and a Python-only fallback table (`_FALLBACKS`) layered on top. The named-builtins file is also a 12-way copy-paste of the same ~13 keys with no shared base.
_Themes:_ Duplicated key contract (Python KNOWN_KEYS vs Rust ThemeOverridesSpec) with live drift, Naming/vocabulary drift across the FFI boundary (font_size, background, per-level grid), Sibling near-duplication (set_default_theme/theme_context; 12 copy-paste builtins)

### rs:transforms (crates/ferrum-core/src/transform/)
_Role:_ The Rust stat engine: a sealed TransformSpec enum of ~41 per-variant transforms that each consume one Arrow RecordBatch and emit one (plus optional named secondary outputs), dispatched by a single macro table.
_Note:_ The dispatch backbone is genuinely elegant: a single `for_each_transform!` macro table (core.rs:120-168) is the one source of truth for the 41 variants, killing the old 5-site fan-out, and `group_key.rs` + `numeric_util.rs` are clean shared utilities introduced exactly to stop sibling drift. The cohesion problems live one layer down, in how individual transforms USE (or fail to use) those shared utilities: the FA-7/FA-12 unification was applied to the data-transform family and to `bin`/`density_data` but left `kde`/`kde_2d`/`smooth` hand-rolling Utf8-only grouping, so the "single source of truth" is bypassed by half the grouped transforms. Extent derivation is reimplemented ~12 times with subtle behavioral drift, and the `groupby` field has fragmented into three incompatible shapes across the family.
_Themes:_ Incomplete unification: shared group_key/extent helpers exist but half the grouped transforms still hand-roll Utf8-only logic, Sibling drift across the stat-transform family (groupby field shape, typed-mode vs flat config, dtype-preserving vs string-only output), Pervasive copy-paste of finite-extent derivation with quiet behavioral divergence, Duck-typed enum-dispatch contract with hard-coded special-case arms

### rs:render-support
_Role:_ The render-support layer turns a resolved ChartSpec + Arrow batch into final pixels/scene-bytes: it ingests Arrow columns (arrow_cast), exposes the PyO3 render/compose surface (binding), applies position adjustments, formats labels, draws/packs mark styling, builds annotations and figure chrome, and composites SVGs.
_Note:_ This is a broad utility tier sitting between scale-resolution and the SVG/WASM emitters. The single-source-of-truth modules (format.rs for d3-format, arrow_cast.rs for dtype dispatch, compositor.rs for clip-id uniquification) are genuinely well-factored and self-aware about their consolidation goal. ### rs:layout (crates/ferrum-core/src/layout/ — axis.rs, mod.rs, legend.rs)
_Role:_ Pure layout engine: maps a ChartSpec + Theme + Viewport into pixel rects for panels, axes (tick placement + collision cascade), and legends/colorbars, touching no data values and doing no rendering.
_Note:_ The subsystem has a clean conceptual spine (a single `compute_layout` orchestrator that reserves bands top-down and delegates per-panel axis/legend placement to typed sub-functions), and the recent B5/Grid work added genuinely good abstractions (the `AxisStyleOverrides`/`TickProjection` bundles, `inset_pixel_range` as a single source of truth). These pairs share an identical underlying concept (measure a label band, carve a strip on an orient, thread overrides onto an output struct) but each was written by copy-and-adapt rather than over a shared core, so the duplication is now structural and the divergences (which override reaches which path) are correctness-by-discipline. `compute_layout` itself is a 615-line god-function mixing five reservation stages.
_Themes:_ Sibling drift between x/y-axis and across the three legend kinds, Duplicated measurement/placement logic with no shared core (struct-build, strip-carve, title-band), Parallel option-bundle drift (LegendOverrides ↔ LegendStyleOpts hand-copied), compute_layout god-function mixing five reservation stages

## All findings (severity-sorted)

### [S4/high/M [API]] (py:render-interactive · sibling-drift) Three parallel save()-format dispatchers with divergent format support and a silently-lossy InteractiveChart.save
- **loc:** src/ferrum/display.py:14-92; src/ferrum/composition.py:323-372; src/ferrum/_interactive.py:236-263
- **problem:** The same concept — 'write this chart-like to disk, dispatching on extension/format' — is implemented three independent times with three different format tables. display.save_chart supports svg/png/html/json/pdf; _CompositeBase.save supports only svg/png/pdf/html (no json, despite compositions being renderable to scene JSON); InteractiveChart.save supports ONLY html and ignores the path extension entirely. The worst seam: InteractiveChart.save(path, **kwargs) pops only embed_wasm/csp_nonce, silently swallows format= and scale=, and unconditionally writes HTML bytes — so chart.interactive().save('foo.png') produces an HTML file with a .png name and no error. _CompositeBase.save('foo.html') forwards **kwargs into it, so a composite-level scale=/format= is silently dropped too. Three dispatchers means a sixth format added tomorrow must be added in three places or it drifts again.

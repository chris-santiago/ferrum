# Bugs #5 / #9 / #10 Fix Design Spec

> Source: open GH bug issues remaining after the KG effort. #5 [FA-11] opacity, #9 [FA-15] conditional-color legend, #10 [R6] interactive label z-order. User decision (2026-06-20): #5 scoped to Option A (fix line + dedup, preserve current opacity semantics; defer composition-semantics unification).

## 1. Scope

Three independent bug fixes: make `mark_line` honor the `fill_opacity` channel and extract a shared opacity resolver across the 5 area/point/bar/line/rect marks (#5); build a color legend from conditional-only color encodings so `bind="legend"` has categories to toggle (#9); fix the interactive label z-order flip on zoom by switching `_placeTextSvg` to a DOM-order-preserving D3 data-join (#10).

## 2. Goals

- **#5:** `mark_line` reads `fill_opacity` (applied to its `FillStroke` style, like `area`/`rect`); the opacity-channel loading/sampling/clamping for `opacity`/`fill_opacity`/`stroke_opacity` is centralized in one resolver used by all 5 marks; each mark's CURRENT opacity semantics are preserved byte-identically except the intended line `fill_opacity` fix.
- **#9:** A chart with `encoding.color = None` plus a conditional color encoding (`when(Color(field))`) renders a categorical color legend whose entries are the conditional field's distinct values, so the interactive `bind="legend"` toggle has categories.
- **#10:** Interactive data labels keep their DOM order (and thus z-order vs raw-overlay groups) across zoom/pan/selection ticks; legend-toggle handlers remain correctly wired after the change.

## 3. Non-goals

- **#5:** Do NOT change opacity-composition semantics across marks — bar.rs's unique `fill_opacity ← opacity` fallback stays as-is; the other marks keep their current (no-fallback) behavior. Unifying the composition model (whether `opacity` is a separate multiplier vs a fallback) is deferred to a follow-up. Do NOT move scale-transform application into the resolver (it stays at each call site).
- **#9:** No WASM/runtime change — the conditional color is already applied at runtime; only the static legend build changes. No change when a base `color` encoding is present (existing path).
- **#10:** No change to the GPU/canvas render path or to what text content/positions are computed — only the DOM update strategy and the dependent legend-handler re-wiring.

## 4. System behavior

- **#5:** `mark_line(...).encode(..., fill_opacity="f")` now varies the line's fill alpha by `f` (was always 1.0). All other marks' opacity output is unchanged. Absent opacity channels → current defaults.
- **#9:** `Chart(...).mark_point().encode(x, y).interactive_color_conditional(...)` (base color unset) now shows a legend with one entry per conditional color category; clicking entries toggles (was: empty legend, dead toggle). A chart WITH a base color encoding is unchanged.
- **#10:** On the first (and every) zoom tick, labels that overlap annotations/axes keep their painted order; legend-entry labels stay clickable. No visible change where labels don't overlap raw geometry.

## 5. Architecture

- **#5** is static-renderer Rust (`crates/ferrum-core/src/render/marks/`). A new `OpacityResolver` value type (load-once, sample per-row or per-group-first) is the single home for opacity-channel resolution; the 5 mark builders construct it and sample it instead of hand-rolling vector loads + clamping. `line.rs` additionally applies the resolved `fill_opacity` to its `FillStroke` (it already builds one via `to_scene_fill_stroke`).
- **#9** is static-render Rust (`crates/ferrum-core/src/render/prepare.rs`). When the base color scale is absent, a helper walks `spec.conditionals` for `ChannelName::Color` branches whose `EncodingValue::Field { name }` names a categorical field, resolves that field's domain via the existing `distinct_values_in_order`, and emits `legend_entries` (+ a legend title from the field). The WASM `bind="legend"` consumer already filters by legend-entry label, so no runtime change.
- **#10** is interactive JS (`src/ferrum/_wasm/ferrum-anywidget.js`). `_placeTextSvg` becomes a D3 data-join; the legend re-wiring (`_wireLegendToggles`) clears its `_ferrumLegendWired` element flag before re-binding, since it previously relied on `_placeTextSvg` destroying+recreating elements to drop stale flags.

## 6. Canonical interfaces / data contracts

**#5 — `OpacityResolver`** (new, in `render/marks/`):
```rust
struct OpacityResolver {
    opacity: Option<Vec<Option<f64>>>,        // `opacity` encoding column
    fill_opacity: Option<Vec<Option<f64>>>,   // `fill_opacity` encoding column
    stroke_opacity: Option<Vec<Option<f64>>>, // `stroke_opacity` encoding column
    general_fallback: bool,                    // bar.rs: fill_opacity falls back to opacity
    defaults: (f64, f64, f64),                 // (opacity, fill_opacity, stroke_opacity)
}
impl OpacityResolver {
    fn load(ctx: &DrawCtx, general_fallback: bool, defaults: (f64,f64,f64)) -> Self;
    fn at_row(&self, i: usize) -> (f64, f64, f64);        // point, bar, rect
    fn at_group_first(&self, first: usize) -> (f64, f64, f64); // line, area
}
```
- `general_fallback = true` ONLY for bar (preserves current behavior); `false` for the others.
- Each `(f64,f64,f64)` element is finite-checked and clamped to `[0,1]`, mirroring current per-mark logic.
- Scale transforms (where point/rect currently map opacity through a scale) stay at the call site — the resolver returns raw-resolved encoding values.
- `line.rs` calls `at_group_first` and assigns the resolved `fill_opacity` to its `FillStroke` (the fix).

**#9 — conditional color legend helper** (in `prepare.rs`):
```rust
fn resolve_conditional_color_domain(spec: &ChartSpec, transformed: &RecordBatch) -> Vec<String>
```
- Iterate `spec.conditionals`; for `cond.channel == ChannelName::Color`, collect `EncodingValue::Field { name }` from `if_selected`/`if_not`; for each field, extend with `distinct_values_in_order(transformed, name)`; dedup preserving first-appearance order.
- Integrated in the legend-build match arm where `provisional_scales.color == None`: if the helper returns a non-empty domain, build `LegendEntry { label, symbol: SymbolKind::Circle }` per value (and set the legend title to the field name, matching the categorical path).

**#10 — `_placeTextSvg` data-join** (in `ferrum-anywidget.js`):
```js
select(svgEl).selectAll('text.ferrum-label')
  .data(texts, keyFn)            // stable key (e.g. content+index)
  .join('text')                  // enter appends; update reuses; exit removes — DOM order preserved
  .attr('class','ferrum-label')  // + x/y/anchor/baseline/font/fill/transform/text from datum
```
- `_wireLegendToggles` clears `el._ferrumLegendWired` on all `text.ferrum-label` before (re)binding, so updated-in-place elements get fresh handlers without duplicates.

## 7. Invariants and constraints

- **#5:** Non-line marks byte-identical. Line changes ONLY where `fill_opacity` is encoded. The `at_row`/`at_group_first` outputs must equal the current inline logic for every mark (same defaults, same finite/clamp handling, same fallback only on bar). Regenerate + visually inspect any golden that byte-diffs (expected only for line+fill_opacity charts); orchestrator blesses PNGs.
- **#9:** Charts with a base color encoding are byte-identical (the new path is gated on `provisional_scales.color == None`). Conditional-color charts that previously had an empty legend now gain entries → regenerate + bless any affected golden. Legend title and symbol match the existing categorical-color legend convention.
- **#10:** Text content/positions unchanged; only DOM update strategy + handler re-wiring change. Legend toggles must still work (verify the flag-clear). No regression in non-overlapping cases.
- No matplotlib; no global mutable state; `cargo test` must pass; goldens visually inspected before commit (orchestrator blesses).

## 8. Key decisions and tradeoffs

- **#5 Option A (user-chosen):** preserve per-mark opacity semantics; the resolver is a dedup + the line fix, NOT a semantics change. bar's `general_fallback=true` flag isolates its quirk without propagating it. The composition-model question (Vega-Lite: `opacity` as separate multiplier) is recorded as a follow-up, not fixed here.
- **#5 resolver excludes scale transforms** — keeping them at call sites avoids changing point/rect scale-mapped opacity behavior (out of scope, risk).
- **#9 static-only** — the conditional color domain is resolvable from the transformed batch at render time; no runtime/WASM change needed since the legend feeds the existing toggle.
- **#10 data-join over remove+append** — the minimal change that preserves DOM order; the only coupling (legend handler flag) is handled by clearing the flag before re-wire.

## 9. Acceptance criteria

- **#5:** `line.rs` reads + applies `fill_opacity`; `OpacityResolver` is the sole opacity-load path in all 5 marks; Rust units assert line + area per-group opacity and confirm point/bar/rect per-row unchanged; `cargo test -p ferrum-core` green; affected goldens regenerated + blessed.
- **#9:** Rust unit: a spec with `color=None` + a `Color` conditional `Field` branch yields non-empty `legend_entries` matching the field's distinct values; base-color charts unchanged; `cargo test -p ferrum-core` green.
- **#10:** `_placeTextSvg` uses a data-join (no `selectAll(...).remove()` + append loop); legend toggles re-wire correctly; `wasm-pack build` + `cargo clippy -p ferrum-wasm` clean; browser/headless check confirms label z-order holds after a zoom tick.
- Full suite: `cargo test -p ferrum-core` + `-p ferrum-wasm` + full pytest all green.

## 10. Validation strategy

#5/#9: fail-before/pass-after Rust units + golden byte-diff (regen + PNG inspection by orchestrator). #10: code-level review of the data-join + flag-clear, then headless-Chrome capture (per the project's puppeteer-core + Chrome.app harness) to screenshot a zoomed chart with overlapping label + annotation and confirm the label paints above — `page.screenshot` is truth (drawImage readback false-blanks). The cargo + pytest suites are the binding gate for #5/#9; #10's gate is the wasm build + the headless visual check (cosmetic, interactive).

## 11. Open questions

- **#5 composition semantics** (deferred per Option A): whether `opacity` should be a separate whole-mark multiplier composing with `fill_opacity`/`stroke_opacity` (Vega-Lite model) rather than bar's fallback. If pursued later, it unifies all 5 marks and removes the `general_fallback` flag — a separate issue with golden blast radius.
- **#10** has no automated test surface (browser-only); validation is the headless capture. Acceptable for a cosmetic interactive fix.
